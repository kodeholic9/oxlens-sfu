## 11. ERR — 실패

실패 응답 body · 오류 코드 번호 공간. 코드의 뜻은 그 코드를 내는 영역의 진술이 인용한다

<a id="RULE-ERR-FLOOR-OUTSIDE"></a>**RULE-ERR-FLOOR-OUTSIDE** · 규칙 — 오류

★★**발언권 실패는 이 절 밖이다.** 발언권은 ★**DC 축**이고(§10), 실패도 그 축에서 온다 —
★**`3 FLOOR_DENY` 의 거절 사유(`2`)**(§10-4-31)이지 `Failure`(§11-1-1)가 아니다.

| | 어디로 오나 | 무엇으로 판단하나 |
|---|---|---|
| WS 요청 실패 | ★**`flags=10` 응답**(§2-1-2) | `code` 앞자리(§11-2-3) |
| ★**발언권 거절·회수** | ★**DC 의 `DENY`·`REVOKE`** | ★**사유 코드**(§10-4-31) |

<a id="RULE-ERR-NOT-MIXED"></a>**RULE-ERR-NOT-MIXED** · 규칙

★**섞이지 않는다** — 발언권 요청은 WS op 이 아니므로 `1xxx`~`5xxx` 가 올 자리가 없다.
★**증상** — 이 경계를 모르면 → 발언권 거절을 ★**WS 오류 처리기로 보내려다** 아무 데도
안 걸려서, 버튼을 눌러도 ★**화면에 아무 반응이 없다.**

### 11-1. 구조

<a id="ERR.type.Failure"></a>
#### 11-1-1. 형 `Failure` — 실패 응답 body
싣는 곳: 모든 op 의 실패 응답(flags=10)

| 칸 | 형 | 필수 | 뜻 |
|---|---|---|---|
| `code` | u16 | ✔ | ★숫자. 판단은 이것으로 한다 |
| `name` | str | ✔ | 로그·사람용. 판단에 쓰지 않는다 |
| `permanent` | bool | ✔ | ★true = 같은 요청을 다시 보내도 같다 |
| `message` | str | — | 없을 수 있다 |
| `details` | json | — | 없을 수 있다 |

<a id="EX-ERR-FAILURE-SHAPE"></a>**EX-ERR-FAILURE-SHAPE** · 예시(비규범) — `Failure` — 실패 응답 body

→ 구조 — [`ERR.example.EX-ERR-FAILURE-SHAPE`](#EX-ERR-FAILURE-SHAPE) · [`ERR.type.Failure`](#ERR.type.Failure)

예시 — 형 `Failure`(형과 대조된 값 · 주석은 칸 설명)

```jsonc
{ "code": 3001,               // ★숫자. 판단은 이것으로 한다
  "name": "ROOM_NOT_FOUND",   // 로그·사람용. 판단에 쓰지 않는다
  "permanent": false,         // ★true = 같은 요청을 다시 보내도 같다
  "message": "…",             // 없을 수 있다
  "details": { } }            // 없을 수 있다
```

<a id="ERR.lead"></a>
#### 11-1-2. 앞자리 — 무엇을 고쳐야 하나

| 앞자리 | 무엇이 잘못됐나 | 클라가 할 일 |
|---|---|---|
| **1xxx** | **요청이 틀렸다** | ★**클라 버그.** 고치기 전엔 다시 보내도 같다 |
| **2xxx** | **신원** | ★**새 토큰을 받는다**(`2003`). ★A 평면에서 클라가 바꿀 수 있는 권한은 없다 — `2005` 는 발급 자격(앱 백엔드 몫), `2006` 은 발행 자격(`permission` 비트 — §7-1-2·§4-2-6)이다. 비트는 서버 밖에서 바뀌므로 새 토큰으로 풀리지 않는다 |
| **3xxx** | **지금 상태에서 안 된다** | 상태를 바꾸고 다시(방에 들어가고, 트랙을 만들고) |
| **4xxx** | **한계에 걸렸다** | 줄이거나 기다린다 |
| **5xxx** | **서버 사정** | 기다렸다 다시 |

### 11-2. 주제

#### 11-2-1. 실패 응답(`flags=10`)을 받았다

<a id="RULE-ERR-CLIENT-FAIL-DEFAULT"></a>**RULE-ERR-CLIENT-FAIL-DEFAULT** · 규칙 — 실패 응답(`flags=10`)을 받았다

0. ★**개별 절차(§3-2-2~§10-4-3)가 그 실패의 처리를 정했으면 그것이 이 절보다 우선한다** — 이 절은 정하지 않은
   실패의 기본값이다(§3-2-2 의 `1xxx` · §4-2-2 의 `3001`·`4001`·`4004`·`4005` · §3-2-3 의 `2008` 이 그 예다).
1. `code` 앞자리로 가른다(§11-2-2).
2. `1xxx` 면 **재시도하지 않는다.** 앱에 버그로 알린다.
3. `permanent:true` 면 **재시도하지 않는다.**
4. 그 밖이면 ★**§3-2-3 사다리의 둘째~넷째 칸(300·1200·2700ms)으로 최대 3회** 다시 보낸다. ★**곧바로 다시 보내지 않는다**(첫 칸 0ms 는 재접속 것이다 — 요청 재시도는 쓰지 않는다). 3회 뒤엔 앱에 알린다(§3-2-3 전체는 재접속 것이다).
5. **상태는 바뀌지 않는다.**

#### 11-2-2. 실패 표현

<a id="RULE-ERR-FAILURE-FORM"></a>**RULE-ERR-FAILURE-FORM** · 규칙 — 실패 표현

실패는 `flags=10`(실패 응답) + body 다.

```jsonc
{ "code": 3001,                  // ★숫자. 판단은 이것으로 한다
  "name": "ROOM_NOT_FOUND",      // 로그·사람용. 판단에 쓰지 않는다
  "permanent": false,            // ★true = 같은 요청을 다시 보내도 같다
  "message": "…",                // 없을 수 있다
  "details": { } }               // 없을 수 있다
```

→ 구조 — [`ERR.type.Failure`](#ERR.type.Failure)

<a id="RULE-ERR-NO-RETRY-AFTER"></a>**RULE-ERR-NO-RETRY-AFTER** · 규칙

★**"얼마나 기다렸다 다시 하라" 는 필드가 없다.** 실패가 답하는 것은 ★**"다시 해도 되나"**
(`permanent`) 하나이고, ★**"언제 다시 하나" 는 클라 백오프가 정한다**(§3-2-3).

<a id="RULE-ERR-4009-SUPPRESS"></a>**RULE-ERR-4009-SUPPRESS** · 규칙

★★**예외는 하나 — `4009` 의 억제값이다**(§11-2-3). 이것은 예측이 아니다. 서버가 여유가 언제 생길지를 맞히는 값이 아니라
★**"적어도 이만큼은 다시 오지 마라"** 는 억제다 — 서버는 자기 수용 한도를 알고, 설정한 기준값을 ★**요청마다 흩뜨려** 준다
(받은 단말들이 같은 순간에 다시 몰리지 않게 — 선례는 3GPP 이동망의 과부하 억제 타이머 `T3346`). ★값이 틀려도 늦게 올 뿐
깨지지 않는다 — 그래서 클라는 그 값을 ★**하한**으로 쓰고, 그 뒤는 자기 규칙대로 다시 보낸다. 위 기각은 예측값에 대한 것이다.

→ 구조 — [`ROOM.C.JOINING.join_4009`](04-room.md#ROOM.C.JOINING.join_4009) · [`ROOM.C.JOINING.retry_join`](04-room.md#ROOM.C.JOINING.retry_join)

<a id="RULE-ERR-PERMANENT-FOR-UNKNOWN"></a>**RULE-ERR-PERMANENT-FOR-UNKNOWN** · 규칙

★**`permanent` 는 모르는 코드용이다.** 아는 코드는 §11-2-3 표가 답하고 앞자리는 대략만 답한다 — `2002`↔`2003` · `3006`↔나머지처럼
★**같은 앞자리 안에서 갈리는 자리**를 이 필드가 덮는다. ★**서버가 코드를 늘려도 클라가 안 깨지게 하는 것이 목적**이다 — §11-2-3 의
*"모르는 코드는 앞자리로 판단한다"* 와 짝이다. ★`LEAVE`(§3-1)에는 이 필드가 없다 — 사유가 닫힌 집합이라 표가 답한다.

<a id="DEV-ERR-LEAVE-PERMANENT-NULL"></a>**DEV-ERR-LEAVE-PERMANENT-NULL** · 자체 확장

`LEAVE` 사유로만 오는 `4006` · `4007` · `4008` · `5004` 의 `permanent` 는 답할 것이 없다(null — 표기 —) — `LEAVE` 에는 이 필드가 없고 사유가 닫힌 집합이라 §3-1 표가 답한다. `1008` 은 `flags=10` 실패 응답으로도 오므로 대역 머리대로 `true` 다

*원문: §11-2-3 대역 머리 "(전부 `permanent` 아님)" — 4xxx · 5xxx 의 LEAVE 사유를 가리지 않고 적었다 · 근거: RULE-ERR-CLIENT-FAIL-DEFAULT*

#### 11-2-3. 앞자리가 "무엇을 고쳐야 하나"다

<a id="RULE-ERR-UNKNOWN-BY-LEAD"></a>**RULE-ERR-UNKNOWN-BY-LEAD** · 규칙 — 앞자리가 "무엇을 고쳐야 하나"다

★★**모르는 코드는 앞자리로 판단한다.** 그래야 서버가 코드를 늘려도 클라가 안 깨진다.
`permanent` 가 오면 그것을 우선한다.
★`LEAVE` 사유로만 오는 `4006` · `4007` · `4008` · `5004` 는 `permanent` 가 없다(null) — 사유가 닫힌 집합이라 LEAVE 사유 표가 답한다 · `1008` 은 실패 응답으로도 오므로 `true` 다(DEV-ERR-LEAVE-PERMANENT-NULL).

#### 11-2-4. 끊을 때 사유 — ★비어 있다(절 번호는 비워 둔다)

<a id="RULE-ERR-CLOSE-EMPTY"></a>**RULE-ERR-CLOSE-EMPTY** · 규칙 — 끊을 때 사유 — ★비어 있다(절 번호는 비워 둔다)

★**이 절은 비었다.** 끊을 때의 사유는 ★**`LEAVE`(§3-1)** 가 나르고 번호는 §11-2-3 와 한 공간을 쓴다. WS Close 에는 코드를 두지 않는다
(정상 종료 `1000` · 그 밖은 아무 코드 — 클라는 보지 않는다). WS Close 대역(`4000~4006`)이 나르던 사유는 `1008`·`4006`·`4007`·`4008`·`2009`·`2010`·`5004` 가
든다. ★종료 사유가 WS 봉투에 눌러 붙어 있으면 전송을 바꿀 때 절이 통째로 붕 뜬다 — §10-4-27 가 RTCP APP 헤더를
걷어낸 것과 같은 규율이다. 절 번호는 비워 둔다(문서 머리의 번호 규율).

### 11-3. 근거 · 기각 — 규격이 아니다

> 계약 본문(구조 · 동작 · 주제)의 규칙이 왜 그런가(R) · 무엇을 하지 않기로 했나(REJ). 소절 머리는 그 근거가 붙은 계약 자리다. 계약 판에는 싣지 않는다.

#### 11-3-1. §11-1-7 5xxx — 서버 사정 (전부 `permanent` 아님)

<a id="R-ERR-SYMPTOMS"></a>**R-ERR-SYMPTOMS** · 근거

★**증상**
- 앞자리를 안 보고 전부 재시도하면 → `1xxx`(클라 버그)에서 **영원히 돈다.**
- `3006` 을 다른 실패와 못 가르면 → **시뮬캐스트를 끄기 전엔 성공할 수 없는데 계속 시도한다.**

#### 11-3-2. §11-2-2 실패 표현

<a id="R-ERR-NO-RETRY-AFTER-WHY"></a>**R-ERR-NO-RETRY-AFTER-WHY** · 근거

★**왜 두지 않나** — 그 시각을 ★**서버가 아는 경우가 없다.** 방이 언제 빌지(`4001`), 미디어 서버가
언제 돌아올지(`5001`)를 서버도 모른다. 모르면서 값을 실으면 클라는 **그 값을 믿고 기다린다** —
★**틀린 값 하나가 백오프를 통째로 대신한다.**
